Docs & rules

Everything about building, submitting and how engines are judged. Values in highlighted text are the current settings and apply to the next round.

Contents

    Quick start

    1. Get your personal token from the organizer. It looks like scc_…, is tied to your name, and is shown only once, so keep it.
    2. Write a chess engine in any language that speaks UCI (a simple text protocol, see The UCI protocol).
    3. Put a Dockerfile at the top of your engine folder. Running the image must start the engine (see Dockerfile templates).
    4. While submissions are open, run ./submit.sh path/to/engine (see Submitting). The server builds it and checks it. Wait for READY.
    5. When the organizer starts a round, your latest ready version plays every other engine. Results appear on the leaderboard.

    Starter engines in Python: random-bot (plays random legal moves, about 60 lines) and minimax-bot (alpha-beta search with time management). Both work as-is.

    How the event works

    The event runs in iterations, all controlled by the organizer from the admin panel:

    1. Submissions open. You can upload new versions of your engine as often as you like. Each upload gets a version number (v1, v2, …) and is built and checked on its own.
    2. The organizer starts a round. This closes submissions. Every player's latest version that passed the checks is entered. If your newest upload failed, your previous ready version plays instead.
    3. The round runs. Games are played automatically, and you can watch them live on the home page.
    4. The round finishes. The leaderboard updates. The organizer opens submissions again for the next iteration.

    Submissions are currently {{ 'open' if settings.submissions_open else 'closed' }}. The organizer can also disable a specific version (for example, if it misbehaves), in which case your previous ready version is used.

    Rules

    Your engine

    • It talks UCI over standard input and output.
    • It is built from your folder's Dockerfile. Any language or library is fine.
    • During games each engine runs in its own container with:
      • {{ settings.engine_cpus }} CPU and {{ settings.engine_memory }} of memory, with no swap. Using more memory gets the engine killed, which loses the game.
      • No network access. The build step does have internet, so pip install, cargo build, downloading files and so on all work at build time.
      • At most 256 processes/threads.
      • A temporary filesystem: anything written is lost when the container stops.

    Time control

    Time control: {{ settings.tc }}, which means {{ tc_text }}. Each engine has its own clock, and the runner tells your engine how much time is left before every move. An engine may overrun its clock by up to {{ settings.timemargin }} ms (to absorb system hiccups). Beyond that, it loses on time.

    You lose a game if your engine

    • runs out of time (beyond the {{ settings.timemargin }} ms tolerance),
    • plays an illegal move or sends a bestmove that isn't a valid move,
    • crashes, exits, or closes its output ("disconnects"), including being killed for using too much memory,
    • stops answering isready ("not responsive").

    These losses are listed in the Problems column of the standings, so you can see what went wrong.

    Draws

    • Normal chess rules: stalemate, threefold repetition, the 50-move rule and insufficient material.
      • {% if settings.maxmoves|int > 0 %}
    • Move limit: a game still going after {{ settings.maxmoves }} moves is a draw.
      • {% else %}
    • There is no move limit.
      • {% endif %}

    Ending decided games early (adjudication)

    {% if settings.adjudicate %}

    Adjudication is on. It uses the scores engines report in their info … score lines (see info lines):

    • Draw: after move {{ draw_adj.movenumber }}, if both engines report a score within ±{{ '%.2f'|format(draw_adj.score / 100) }} pawns ({{ draw_adj.score }} centipawns) for {{ draw_adj.movecount }} moves each in a row. The count restarts after any capture or pawn move.
    • Loss: if both engines agree that one side is at least {{ resign_adj.score // 100 }} pawns down ({{ resign_adj.score }} centipawns), or getting mated, for {{ resign_adj.movecount }} moves each in a row. The losing side loses the game.

    Both engines must agree, so a single engine with a broken evaluation can't end a game by itself. An engine that never reports a score is never adjudicated: its games are played to the end.

    {% else %}

    Adjudication is off: every game is played until it ends by the rules above.

    {% endif %}

    How a round is played

    • Round-robin: every engine plays every other engine.
    • Openings: games don't start from the initial position. Each one starts from an opening taken from the {{ book_name }} book (the book used to test Stockfish): 8 moves by each side are already on the board, so your engine takes over at move 9. This gives variety and stops one engine winning every game with the same line.
    • Both colours: each opening is played twice by the same two engines, once with each colour, so neither side is helped by a lucky opening.
    • Per pairing: {{ settings.rounds }} openings × 2 colours = {{ settings.rounds|int * 2 }} games. Openings are drawn at random, with a new random order every round.
    • Round size: {% if n_engines >= 2 %}with the {{ n_engines }} engines that are ready right now, that's {{ n_pairs }} pairings and {{ n_games }} games. {% else %}there are not yet two ready engines (a round needs at least two).{% endif %} In general: players × (players − 1) / 2 × {{ settings.rounds|int * 2 }} games.
    • Parallel games: {{ concurrency }} games run at the same time. Each engine has its own CPU and memory limits, so games don't slow each other down.
    • Engine processes are reused. An engine is started once and then plays several games in a row. Before each game it receives ucinewgame, so clear any per-game state (hash tables, history) then. If an engine crashes, it loses that game and is started again for its next one.

    Scoring and the leaderboard

    • A win is worth 1 point, a draw ½, a loss 0.
    • Engines are ranked by points. Ties are broken by Sonneborn-Berger (results against stronger opponents count more: for each opponent, your score against them × their total points, summed up), then by Elo.
    • Elo is estimated from this round's games only (the Bradley-Terry model, the maths behind Elo ratings). The average engine is 0. The ± is a 95% confidence range: with few games it's wide, so two engines whose ranges overlap may really be equally strong. These numbers are relative to this event and can't be compared with chess.com or Lichess ratings.
    • Standings columns: Points, Games, W / D / L (wins, draws, losses), Score (points as a percentage), Elo, and Problems (games lost on time, by illegal move or by crashing).
    • The cross table shows the points each engine scored against each other engine.
    • The home page shows the latest completed round. Older rounds are under Rounds & games. Rounds that were cancelled or failed (for example, if the server restarted) don't count.

    Submitting

    With the submit script (macOS / Linux / WSL):

    curl -fsSL {{ url }}/submit.sh -o submit.sh
chmod +x submit.sh
export SCACC_TOKEN=scc_your_token_here     # or save it in ~/.scacc-token
./submit.sh path/to/your/engine

    The script packs the folder (leaving out .git, node_modules, target, build, __pycache__ and .venv), uploads it, and streams the build and check log until it says READY or why it failed.

    Without the script:

    tar czf engine.tgz -C path/to/your/engine .
curl -H "Authorization: Bearer $SCACC_TOKEN" -F engine=@engine.tgz {{ url }}/api/submit
# the response has an "id"; follow the log with:
curl -H "Authorization: Bearer $SCACC_TOKEN" {{ url }}/api/submissions/<id>/log
    • Upload a .tar.gz or .zip of at most {{ max_upload_mb }} MB. The Dockerfile must be at the top level (a single wrapping folder is fine too).
    • You can only upload while submissions are open, and only one build at a time: wait for the previous one to finish.
    • Check your token and versions with curl -H "Authorization: Bearer $SCACC_TOKEN" {{ url }}/api/me.

    What the server checks

    Every upload goes through two steps. Only versions that pass both are used in rounds.

    1. Build

    The server runs docker build on your folder, with internet access and a {{ build_timeout_min }}-minute time limit. The full build log is streamed back to you.

    2. Smoke test

    The image is started with the same limits as in games (no network, {{ settings.engine_cpus }} CPU, {{ settings.engine_memory }}) and must:

    1. answer uci with uciok within 30 seconds, then isready with readyok;
    2. for each of these 4 positions, after ucinewgame, isready, the position command and go wtime 10000 btime 10000 winc 100 binc 100, reply with a legal bestmove within 6 seconds:
      • position startpos
      • position startpos moves e2e4 e7e5 g1f3 (black to move)
      • position fen r1bqkb1r/pppp1ppp/2n2n2/4p2Q/2B1P3/8/PPPP1PPP/RNB1K1NR w KQkq - 4 4 (mate in one available)
      • position fen 8/P5k1/8/8/8/8/6K1/8 w - - 0 1 moves g2f3 g7f7 (FEN plus moves, a promotion is possible)

    The engine's id name becomes the engine name shown on the leaderboard. Anything it prints on stderr is included in the log, which is handy for debugging.

    The UCI protocol

    UCI (Universal Chess Interface) is how chess programs talk to engines. It's plain text: the runner writes one command per line to your engine's stdin, and your engine answers with lines on stdout. Every line ends with a newline, and your engine must flush stdout after every line, or the runner never sees it.

    A full session, as the runner does it

    > uci                                    # once, when the engine starts
< id name MyBot 1.0
< id author Alice
< uciok
> isready
< readyok

> ucinewgame                             # before every game
> isready
< readyok

> isready                                # before every move: are you still alive?
< readyok
> position startpos moves e2e4 c7c5 g1f3 d7d6 d2d4 c5d4 f3d4 g8f6 b1c3 a7a6 c1e3 e7e5 d4b3 c8e6 f2f3 b8d7
> go wtime 9820 btime 9950 winc 100 binc 100
< info depth 1 score cp 18 nodes 31 pv d1d2
< info depth 2 score cp 12 nodes 240 pv d1d2 f8e7
< info depth 3 score cp 25 nodes 1900 pv d1d2 f8e7 e1c1
< bestmove d1d2

  … the same isready / position / go / bestmove for each of your moves …

> quit                                   # when the engine isn't needed any more

    > = runner to engine, < = engine to runner. Text after # is a comment here, not part of the protocol.

    Commands your engine receives

    CommandWhat to do
    uciPrint id name … and id author … (optional), then uciok. You have {{ startup_s }} seconds, including container start-up.
    isreadyReply readyok right away. It is sent at start-up, before each game and before each move.
    ucinewgameA new game starts: reset per-game state (hash table, killer moves, history…). No reply.
    position startpos moves …
    position fen <FEN> moves …    		Set up the board. The move list is always the whole game so far, including the 16 opening-book moves, so the simplest approach is to rebuild the board from scratch every time. No reply.
    go wtime W btime B winc WI binc BIThink, then print bestmove <move>. Times are in milliseconds: remaining time for white and black, and the increment each gets after a move. Only your own clock matters (wtime if you are white). If the time control has a move count, movestogo N is added.
    stopStop thinking and print bestmove immediately. During games the runner does not send it; it only comes at the very end, together with quit. Your engine must decide on its own when to stop.
    quitExit.
    setoption, debug, ponderhit, registerNot sent in this event. If you receive an unknown command, ignore it.

    Move format

    • From square + to square, lowercase: e2e4, g8f6.
    • Castling is the king's move: e1g1 (white short), e1c1 (white long), e8g8, e8c8.
    • Promotion adds the piece letter in lowercase: e7e8q (or r, b, n).
    • En passant is just the pawn's move, e.g. e5d6.

    info lines (optional, recommended)

    While thinking, an engine can print progress lines, for example info depth 6 score cp 25 nodes 12000 pv g1f3 b8c6:

    • depth N: how many half-moves ahead this search looked.
    • score cp N: evaluation in centipawns (100 = one pawn) from your engine's point of view: positive means good for the side to move. score mate N means you see a mate in N moves; a negative N means you are getting mated.
    • pv …: the line you expect, starting with the move you intend to play.
    • nodes, nps, time: statistics, shown nowhere but harmless.
    • info string anything: free text, useful for debug output.

    The score from your last info line before bestmove is recorded with the move. It is shown in the game viewer, and it's what adjudication is based on. Engines that don't print scores work fine; they just show "no score" and their games are always played out.

    Time management

    Your engine is responsible for not running out of time. A simple, safe budget per move:

    budget = my_time_left / 30 + my_increment * 0.8
    {% if budget_ms %}

    With the current time control ({{ settings.tc }}) your clock starts at {{ base_ms }} ms{% if inc_ms %} with {{ inc_ms }} ms added per move{% endif %}, so the first move's budget is about {{ budget_ms }} ms. Check the clock during your search too, not only between depths, and keep a safety margin: starting a process and passing messages costs a few milliseconds per move.

    {% endif %}

    Output rules

    • Only print UCI lines on stdout. Put debug output on stderr, or in info string … lines.
    • Flush after every line: print(..., flush=True) or python -u in Python, std::endl or fflush(stdout) in C/C++, io::stdout().flush() in Rust, System.out.flush() in Java.
    • Keep reading stdin while idle: isready must be answered promptly.

    Testing locally

    Build your image and feed it a few commands, the same way the server does:

    docker build -t my-engine .
(printf "uci\nisready\nucinewgame\nposition startpos moves e2e4\ngo wtime 10000 btime 10000 winc 100 binc 100\n"; sleep 3; echo quit) \
  | docker run -i --rm --network none --cpus={{ settings.engine_cpus }} --memory={{ settings.engine_memory }} my-engine

    You should see uciok, readyok and a bestmove line. Use -i only, not -it: a terminal (-t) changes how output is buffered.

    To play real games between two engines on your machine, use fastchess (what this server uses) or cutechess. Point both at docker run -i --rm my-engine as the engine command.

    Dockerfile templates

    The image's ENTRYPOINT (or CMD) must start the engine, reading UCI from stdin. It runs without arguments, a terminal or network.

    Python

    FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ENTRYPOINT ["python3", "-u", "engine.py"]

    C++

    FROM gcc:14 AS build
WORKDIR /src
COPY . .
RUN g++ -O2 -std=c++20 -o engine *.cpp

FROM debian:bookworm-slim
COPY --from=build /src/engine /engine
ENTRYPOINT ["/engine"]

    Rust

    FROM rust:1.83 AS build
WORKDIR /src
COPY . .
RUN cargo build --release

FROM debian:bookworm-slim
COPY --from=build /src/target/release/my-engine /engine
ENTRYPOINT ["/engine"]

    Multi-stage builds (compile in a big image, copy the binary into a small one) keep images small and start-up fast.

    Common mistakes

    • Not flushing stdout. The check fails with "no 'uciok' line within 30s". Flush after every line.
    • Ignoring the clock. An engine that always thinks for a fixed time eventually loses on time. Read wtime/btime and budget.
    • Only handling startpos. Games start from book positions, and the smoke test uses position fen … moves ….
    • Keeping state between games. The engine process is reused, so reset on ucinewgame, and don't let memory grow game after game: past {{ settings.engine_memory }} the engine is killed.
    • Using more threads than CPUs. You have {{ settings.engine_cpus }} CPU; extra threads just compete for it.
    • Downloading things at runtime. There's no network during games. Fetch everything (opening books, neural networks, tablebases) in the Dockerfile.
    • Wrong move format. e7e8Q (uppercase) or SAN like Nf3 are illegal moves. Use e7e8q and g1f3.

    Watching games

    • Live games appear on the home page while a round runs. Click one to follow it move by move.
    • Every finished game can be replayed from Rounds & games. Filter by player, colour, opponent, result or how the game ended.
    • In the game viewer: use ← → to step through moves, f to flip the board, and Copy PGN to copy the game. Under the board you'll see the score each engine reported for its own move.
    • Switch on Stockfish 19 analysis (or press L) to see the best move as an arrow, an eval bar and the best lines. It runs in your browser, so it never slows down the tournament.
